調査日：2026年10月30日〜31日 ／ 出典は GitHub・npm・crates.io 等の公式情報を優先

日本語形態素解析ライブラリ調査小説執筆エディター（novelaide / novelaid-editor）のための、Node.js 系と Rust 系の比較

用途はルビ（ふりがな）自動付与、校正支援、表記ゆれ検出、本文検索のための分かち書き。そして追加要件として、登場人物名や地名などの造語を「読み」付きで実行時に登録できるか（ユーザー辞書）を最重要の確認項目とした。結論は両系統とも Lindera —— エンジン・辞書・ユーザー辞書ファイルを Electron 版と Tauri 版で共通化できるのが決め手になる。

Q1. おすすめはどれか

Rust・Node とも Lindera が第一候補

Rust 側の次点は Vibrato。Node 側の次点は条件付きで kuromoji 系の保守フォーク（ユーザー辞書なしを割り切れる場合のみ）。

Q2. ユーザー辞書は使えるか

Lindera は「3列CSV」だけで登録できる

表層形・品詞・読みだけの簡易 CSV を読み直し、プロセス内で Tokenizer を再構築すれば即反映。kuromoji 系は公式対応なし。

Q3. 読み仮名は形態素解析の機能か

はい。標準機能に含まれている

形態素解析は形態素ごとに「表記・品詞・原形・読み」をセットで返す。ルビ自動付与は、その読みをそのまま使うのが王道。

Rust 系Tauri 製エディター（novelaide）向け
第一候補

Lindera 6.2.0

2026-09-26 リリースと最も活発。純 Rust で辞書埋め込み可。品詞・原形・読み・発音が揃い、ユーザー辞書は簡易 CSV 3列で最も簡単。

@faanau/kuromoji（保守フォーク）

純 JS で組み込みが最も楽、実績も最大。ただしユーザー辞書は公式非対応。「読み替え表をアプリ側で別途持つ」割り切りができる場合に限る。

npm install @faanau/kuromoji

共通化の利点：両系統で Lindera を使えば、作品ごとの用語集（登場人物名＋読み）を同じ簡易 CSV で一元管理でき、ルビの付き方・表記ゆれ判定・分かち書き境界が系統間で一致する。先に Electron 版を WASM で作り、後から Tauri 版を作る段階的移行でも、解析層をほぼそのまま移植できる。

01

読み仮名は、形態素解析の標準機能

ルビ自動付与の実装観点

形態素解析は文を形態素に分けるだけでなく、各形態素について品詞・原形・読み（ヨミ）・発音を辞書エントリからセットで返す。だからルビ付与は「解析して、各形態素の読みをルビにする」で完結し、文脈で読みが変わる語（「今日＝きょう」「明日＝あした」）も、採用された辞書エントリの読みがそのまま返る。ライブラリごとに読みを取り出すフィールド名が違うのが実装上の要点になる。

注意点が2つある。第一に、IPADIC 系の「読み」は原則カタカナなので、小説のルビ（通常ひらがな）にするにはカタカナ→ひらがな変換が別途必要（自前実装は容易）。第二に「読み」と「発音」は別フィールドで、発音は長音・撥音を反映した形（例：関西国際空港の発音はカンサイコクサイクーコー）。ルビにどちらを使うかはエディター側のポリシーとして決める。

読みの取り出し方エクスプローラー

ライブラリを選ぶと、読みの取得方法と、確定している実例（Lindera 公式サンプルの「関西国際空港」）でのルビ表示を確認できる。

02
ユーザー辞書 ― 動的な単語追加の可否が分かれ目
登場人物名・地名・造語を読み付きで登録する

    
小説エディターでは、作品固有の人名や造語に正しい読みを持たせて登録し、ルビ・校正・分割すべてに反映したい。この「実行時の単語追加」への対応が、今回の調査で最も大きく明暗を分けた。対応していても登録フォーマットの重さがまったく違い、エディターの「作品用語集」UI と直結させやすいかどうかが実用性を決める。


    

      

        

          
Lindera 対応 ◎ 最も簡単

          
簡易 CSV は3列だけ。コストや左右文脈IDは不要。load_user_dictionary(path, &metadata) で読み込み、Segmenter / Tokenizer をプロセス内で再構築すれば反映される。辞書コンパイルもアプリ再起動も不要。

          
東京スカイツリー,カスタム名詞,トウキョウスカイツリー
# 列: 表層形, 品詞, 読み

        

        

          
Vibrato 対応 ○ 実行時差し替え可

          
Dictionary のユーザー辞書を reader からリセットする API があり、None でクリアもできる。Tokenizer を作り直さず差し替えられるのは強い。ただし CSV は MeCab 形式フル仕様で、左ID・右ID・コストをアプリ側で用意しなければならない。

          
神保町,1293,1293,334,カスタム名詞,ジンボチョウ
# 列: 表層形, 左ID, 右ID, コスト, 品詞, 読み（CLI 例より）

        

        

          
sudachi.rs 可能 △ バイナリ化が必須

          
登録は Sudachi 形式 CSV を sudachi ubuild でバイナリ user.dic にコンパイルし、sudachi.json の userDict に指定して Tokenizer を（再）生成する方式。1語をコードから即時追加する API は公式ドキュメントに見当たらない。しかも辞書形式が v202610 から V1 になり V0 と非互換 ― システム辞書を更新したらユーザー辞書も作り直しが必要。

        

        

          
kuromoji 系 非対応 ×

          
GitHub Issue #18「User dictionary support」は長年の未解決 TODO で、保守フォーク @faanau/kuromoji の README でも「user dictionaries (#18) are not addressed yet」と明記。回避策として辞書全体の再構築が非公式に知られるのみで、公式 API はない。登場人物名＋読みの登録はこのエンジン単体ではできない。

        

        

          
MeCab 系 / Vaporetto 本用途には不適

          
MeCab 本体は CSV を mecab-dict-index で .dic 化する方式で、実行時の増分追加 API はない。Vaporetto は実行時 API 自体がなく、語彙は学習時に与えるか、モデルを dump → 編集 → 再投入する外科的編集のみ。

        

      


      

        
ユーザー辞書があると何が変わるか

        
概念図：Lindera の簡易 CSV に 東京スカイツリー,カスタム名詞,トウキョウスカイツリー を登録した場合の分割と読みの違い（実測出力ではなく仕組みの説明）。

        

          
          ユーザー辞書：OFF
        

        

        
登録した語は1形態素として扱われ、登録した読みがそのままルビになる。未登録の固有名詞は、既存の語に割れて読みもずれる恐れがある ― 小説では人名で起きやすい問題。

パッケージ
crates.io: lindera = { version = "6", features = ["embed-ipadic"] }。解析チェーンは companion crate lindera-analysis = "6"（v5 以降、コアは Segmenter に分離）

          
メンテナンス
非常に活発。最新 v6.2.0（2026-09-26）、v6.1.0 が同9-25、v6.0.0 が同8-25。main では次期 v7 の表記も見えるが、引用すべき最新版は 6.2.0

          
ネイティブ依存
なし（純 Rust）。Windows 向け CLI バイナリも公式リリース資産に含まれる

          
辞書
IPADIC、IPADIC-NEologd、UniDic、SudachiDict（v6.0.0 で lindera-sudachidict 追加）、韓国語 ko-dic、中国語 CC-CEDICT / Jieba。埋め込みは feature で選択（embed-ipadic 等）。埋め込まない場合は GitHub Releases のビルド済み辞書を load_dictionary(path) で読む。mmap feature がデフォルト有効

MIT

速度
公式 README：「IPADIC で概ね 10–20 MB/s（シングルスレッド）」。ベンチマークスイートがリポジトリに同梱

      sudachi.rs正規化・同義語情報が表記ゆれ検出に最も強いが、組み込み上の課題が多い
      

        

          
パッケージ
注意点：公式 README の ToDo に「Registration to crates.io」が残っており、通常の crates.io 依存として取得できるかは未確認。公式に案内される手順は git clone ＋ cargo build --release ＋ cargo install --path sudachi-cli/

          
メンテナンス
活発（リリース 14 件、SudachiPy 0.7.0 が 2026-10 月にパッケージ化）。ただし v0.7 系について公式が「Release v0.7.* is unstable. パッチ間でも破壊的変更がありうるので正確なバージョンを固定せよ」と警告

なし（純 Rust）

SudachiDict（同梱なし、別途ダウンロード）。Small（UniDic 語彙のみ）／Core（デフォルト）／Full（固有名詞を増強）の3版。Core のダウンロードが約 70 MB（SudachiPy README）、sudachidict_core の wheel（20261015）が 76.9 MB、conda では small 約 27.6 MB／core 約 51.4 MB（いずれも概数）。辞書バイナリ形式が v202610 から V1 になり、V0 と互換性がない

06
補足：漢字→読み変換専用ツール
形態素解析とは別区分の選択肢

    
「読みを取る」だけなら変換専用ツールという区分もある。ただし位置づけは大きく違う。kuroshiro は中身が形態素解析の“表示層”、KAKASI 系は品詞を持たない辞書照合型で、文脈による読みの自動選択機構がない。


    

      

        
kuroshiro ― ルビ出力まで一括の変換層

        
npm install kuroshiro

        
    
          
  • convert(str, {to, mode}) が API の中心。to は hiragana / katakana / romaji、mode の furigana は HTML の <ruby> タグを直接出力する。MIT。
    • 
          
  • 中身は形態素解析。解析器はプラグイン式で、公式に kuroshiro-analyzer-kuromoji（kuromoji / IPADIC）と kuroshiro-analyzer-mecab（要 MeCab）。読み分けの能力は内側の解析器と等しい。
    • 
          
  • 限界：返るのは変換済み文字列のみで、形態素の配列を受け取る API はない。校正や表記ゆれには別途形態素解析が必要。ユーザー辞書も内側の kuromoji が非対応のため登録できない。
    • 
          
  • メンテナンス：1.x 系は長く更新がなかったが、公式リポジトリでは現在 Version 2（beta、Node 22+ 前提） の開発が進行中。2.0 の正式リリース時期は未確認。
    • 
        

        
出典：github.com/hexenq/kuroshiro（2026-10-30 取得）

      

      

        
KAKASI 系 ― 辞書照合型の変換器

        
    
          
  • 「漢字→かな（ローマ字）変換プログラム」（C 言語、本家は GPL v2 以降）。名称は "kanji kana simple inverter" の略。辞書の大部分は SKK 辞書に由来し、熟語辞書（kanwadict）と異体字辞書（itaijidict）を使う。品詞や接続コストを持たないため、形態素解析器ではない。
    • 
          
  • 読み分け：文脈で読みを自動選択する機構がない。公式 manpage の -p オプションが傍証 ― 複数読みは「素子 → {もとこ|そし}」のように列挙できるだけで、1つの選択は利用者側に委ねられる。
    • 
          
  • ユーザー辞書：追加辞書は SKK 形式で「読み, 熟語」の2フィールド。品詞がないため、登録しても読み変換にしか効かず、分割や校正の改善にはつながらない。
    • 
          
  • Python 移植の pykakasi が現行の利用形態として知られるが、npm / crates.io における現行の KAKASI 本体パッケージは未確認。異体字→新字体の変換（itaijidict）は伝統的に得意。
    • 
        

        
出典：kakasi.namazu.org ／ Debian manpage（2026-10-31 取得、インデックス）

      

    


    

      

        
観点形態素解析ベースkuroshiroKAKASI 系

        
          
変換の仕組み品詞・接続コストを持つ辞書＋文脈で分割を最適化し、採用された語エントリの読みを返す内側は形態素解析（kuromoji 等）。能力は解析器に依存品詞・コストを持たない熟語辞書の照合（最長一致的）のみ

          
文脈依存の読み分け「今日」「明日」「一日」「上手」のような語でも、文の構造を使って分割と読みの組を選べる余地がある。最終的な読みは採用された辞書エントリで決まるkuromoji 準拠自動選択の機構なし。複数候補は -p で列挙できるだけ

          
送り仮名・活用活用形情報を辞書が持ち、語幹と活用語尾を分けて処理できるkuromoji 準拠辞書の熟語エントリ頼み。活用に伴う読みの変化への対応は弱い

          
固有名詞（造語・人名）ユーザー辞書を持つエンジンでは「表記＋読み＋品詞」で登録でき、分割・ルビ・校正すべてに反映内側の kuromoji が非対応のため登録不可SKK 形式で「読み＋表記」は足せるが、品詞がないため読み変換にしか効かない

          
得られる情報品詞・原形・読み・発音など（校正・表記ゆれ・検索に転用可能）変換済み文字列のみかな／ローマ字文字列（＋分かち書き）のみ

          
異体字辞書次第（Sudachi は正規化プラグインが強い）解析器次第itaijidict による異体字→新字体の変換は伝統的に得意

        
      

    

    
整理すると、文脈で読みが揺れる語や作品固有の人名を正しく扱うには、文脈情報を持つ形態素解析ベースが構造的に有利。KAKASI 系は「辞書に載っている読みを引く」軽量な変換器、kuroshiro は「形態素解析の結果をルビ付き文字列に整形する表示層」と位置づけるのが正確。

  


  
  

    
07
推奨の理由と、採用時の進め方
小説執筆エディター用途での判断

    

      

        
Rust 系：Lindera →（次点）Vibrato

        
    
          
  • Lindera はメンテナンスが最も活発で、純 Rust・辞書埋め込みにより Tauri への同梱が素直。
    • 
          
  • 品詞・原形・読み・発音が揃い、ルビ・校正・表記ゆれ（原形ベースの集計）・分かち書き検索の全用途を1エンジンでまかなえる。
    • 
          
  • 決め手はユーザー辞書：3列 CSV だけで人名・造語を読み付きで登録でき、コスト計算や文脈IDの知識なしに「作品用語集」UI と直結させやすい。
    • 
          
  • 辞書はまず IPADIC（軽量）で始め、固有名詞の不足が気になれば UniDic や NEologd 埋め込み（大型化は要実測）、あるいは SudachiDict も同じエンジンのまま選択できる。
    • 
          
  • Vibrato は MeCab 互換が欲しい場合や解析速度を最優先する場合の選択肢。ユーザー辞書 CSV の重さと、辞書の別途配布・zstd 展開が代償。
    • 
          
  • sudachi.rs は解析品質目当てなら有力だが、crates.io 登録の未確認、0.7 系の不安定警告と辞書形式の非互換、ubuild 必須の三点が組み込みコストを押し上げる。将来の再評価候補。
    • 
        

      

      

        
Node 系：Lindera 系 →（条件付き次点）kuromoji 系

        
    
          
  • Lindera 系は Rust 側と同じエンジン・辞書・ユーザー辞書形式を使え、解析結果が系統間で一致する。ユーザー辞書と読みの取得に対応する唯一の現行選択肢。
    • 
          
  • ネイティブ版 lindera は速度と実装の素直さで有利だが、Electron のネイティブモジュール配布（asar 外への展開、アーキテクチャ別 prebuilt）の手間がある。
    • 
          
  • lindera-wasm はその手間を避けられる代わりに、辞書の実行時ロード設計とバンドラ設定が必要。どちらを選ぶかはパッケージング方針次第。
    •

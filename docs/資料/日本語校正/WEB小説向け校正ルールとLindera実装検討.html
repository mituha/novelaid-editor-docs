WEB小説向け校正ルールと
Linderaによる実装検討

textlint の技術文書向けプリセットは、小説にそのまま当てると誤検出が多発する。必要なのはプリセットの流用ではなく、WEB小説の作法に合わせたルールの選別と強さの再設計だ。本稿ではルールを5分類して必要度を付け、textlint での対応と、Lindera（形態素解析）で自前実装する場合の処理方式を対応づける。

結論1 ― 選別が先、実装は後

効くルールの大半は「体裁・タイプミス」と「表記ゆれ」。文法系は会話文を除外するスコープ制御とセットで初めて実用になる。

結論2 ― 実装は3層に分ける

正規表現で済む層、辞書マッチの層、Lindera のトークン列パターンが要る層。形態素解析は第3層だけでよく、全ルールを Lindera に寄せない。

結論3 ― 辞書が共通資産になる

Lindera のユーザー辞書CSV（分割・読み用）と prh 形式の表記統一辞書は役割が別で、両方要る。この2つを novelaid-editor／novelaide で共有するのが共通化の軸。

00

前提：技術文書向けプリセットはそのまま使えない

textlint の代表プリセット preset-ja-technical-writing は技術文書向けに調整されている。小説との代表的な衝突と、本稿での扱いを先に固定する。

プリセットの既定小説での実態扱い本稿の方針
一文の長さ上限（100字）小説では長文も普通に使う大幅緩和エラーにせず、目安表示（情報レベル）に留める
読点は1文に3つまで地の文では普通に超える無効化〜緩和既定オフ。気になる作品だけ上限を大きく取って有効化
！？の使用禁止WEB小説では通常の表現反転させる禁止ではなく「直後に全角スペース」等の使い方の作法チェックにする
ですます／であるの文体統一地の文には有効だが、会話文はキャラの口調範囲を限定地の文のみに適用し、会話文は適用外
弱い表現・冗長表現の検出あえて使う表現も多い格下げ既定では無効〜情報レベル。書き手が意図を確認する材料に留める
必要度の凡例： ◎ ほぼ必須 ○ あると助かる △ 作品の方針次第 × 小説では無効化推奨
01

ルールカタログ

分類ボタンと必要度ボタンで絞り込める。各ルールには「textlint での対応」と「Lindera 実装での方式」を併記した。方式は 文字列（正規表現・段落処理）／辞書（prh形式などのマッチ）／トークン（Lindera の形態素列パターン）／集計（文書全体の統計）の4種。

02

    03

    Lindera でどう処理するか

    校正エンジンの全体像は「前処理で範囲を決め、層ごとに判定し、診断として集約する」パイプラインになる。Lindera が担うのは形態素解析と、その結果（トークン列）へのパターンマッチだけに絞るのが要点。

    処理パイプライン

    1. 段落・文分割段落単位に分け、「。！？」で文に切る
    2. スコープ判定「」『』内を会話文、それ以外を地の文として範囲タグ付け
    3. 文字列層正規表現ルール（A分類）を原文に直接適用
    4. 形態素解析文ごとに Lindera で解析し、トークン列＋ユーザー辞書を適用
    5. 辞書・トークン層辞書マッチ（B）とトークン列パターン（C・D）を判定
    6. 診断の集約位置・重要度・適用範囲つきでエディターへ返す

    3層モデル：ルールを重さで仕分ける

    LAYER 1

    文字列層 ― 正規表現

    括弧対応、字下げ、三点リーダーの偶数個、記号の重複など。形態素解析なしで検出でき、誤検出が少なく効果が確実。まずここから実装する。対象は主にA分類。

    LAYER 2

    辞書層 ― prh形式マッチ

    固有名詞の統一、漢字の開き／閉じポリシー、誤用語など「語の対応表」で書けるもの。prh.yml 互換の辞書データにすれば textlint 側と資産を共有できる。対象は主にB分類。

    LAYER 3

    トークン層 ― Lindera

    ら抜き、助詞の連続、文体判定など、品詞・原形・活用情報が要るもの。Lindera のトークン列に対するパターン定義としてルールを書く。対象は主にC・D分類。

    トークンから何が取れるか

    IPADIC 系辞書では、各トークンの details に「品詞、品詞細分類1〜3、活用型、活用形、原形、読み、発音」が並ぶ（MeCab の素性順）。校正で主に使うのは品詞・活用型・活用形・原形・読みの5つ。ユーザー辞書に登録した語は1トークンとして返り、登録した読みがそのまま付く。

    「天霧澪は剣を取った。」の解析イメージ

    ルールの書き方：トークン列パターンの例

    ら抜き言葉は「一段・カ変動詞の未然形相当＋助動詞『れる』」というトークン列のパターンで表せる。会話文スコープを外す設定と組み合わせることで、地の文だけに警告を出す指定が可能になる。

    // 概念コード：ら抜き検出（地の文スコープのみ）
for sentence in sentences where sentence.scope == Narration {
    for (a, b) in tokens.windows(2) {
        if a.pos == "動詞" && a.conjugation_type in ["一段", "カ変・來ル"]
           && b.surface == "れる" && b.pos == "助動詞" {
            report(Warning, range_of(a, b),
                   "ら抜き言葉の可能性があります（地の文）");
        }
    }
}
    • 助詞の連続：トークン列で助詞「の」が短い間隔に3回以上、等のカウント判定。
    • 助詞の重なりミス：同一助詞トークンの完全連続（「にはには」）を検出。タイプミス的なので重要度は高くてよい。
    • 送り仮名のゆれ：原形が同じ動詞を文書全体で集計し、表層の送り仮名が複数形に割れていたら提示する（集計型）。
    • 文体統一：文末トークン（です／ます／だ／である）を文ごとに判定し、地の文の多数派と違う文を挙げる（集計型）。

    辞書は2種類、役割を分ける

    Lindera ユーザー辞書CSV ― 「どう切るか・どう読むか」

    形式は 表層形,品詞,読み の3列。登場人物名や固有の技名を登録すると、1トークンとして切れ、読みが付く。効く先は形態素解析の精度そのものと、ルビ自動付与。読み込み直せば再起動なしで反映される。

    天霧澪,固有名詞,アマギリミオ
星屑の剣,固有名詞,ホシクズノツルギ

    prh形式の表記辞書 ― 「どう書くべきか」

    「ゆれ候補 → 正規表記」の対応表。固有名詞の表記統一、漢字の開き／閉じ、一人称の統一などに使う。textlint の textlint-rule-prh と同じ prh.yml データを両エディターで読み合える形にしておくと、辞書育成が片方に偏らない。

    # prh.yml のイメージ
- expected: 天霧澪
  patterns: [天霧みお, あまぎり澪]
- expected: できる
  patterns: [出来る]
    注意：ユーザー辞書CSV は「分割と読み」のため、表記ゆれの検出そのものは行わない。逆に prh 辞書は表記を直す先を示すが、解析の切り方は変えない。混同して片方だけで済ませようとすると、固有名詞が途中で割れて検出漏れが出る。

    適用範囲（スコープ）と重要度の設計

    設計軸内容
    スコープルールごとに「地の文のみ／会話文のみ／両方」を設定可能にする。判定は「」『』の範囲で機械的に行い、括弧が閉じていない箇所はスコープ不明として文法系を適用しない
    重要度エラーの3段階。エラー＝体裁・タイプミス系（Aの◎）、警告＝文法系・表記ゆれ、情報＝読みやすさの目安（一文の長さ等）。小説では「情報」を増やし「エラー」を絞るのが既定方針
    部分再解析編集中は変更のあった段落だけを再解析し、診断を差し替える。文書全体の集計型ルール（送り仮名・文末の連続など）は保存時や手動実行に回す
    例外の登録「この表現は意図的」を作品単位で例外登録できること。誤検出を消せない校正は、結局オフにされる
    04

    2つのエディターでの構成と実装順

    novelaid-editor（Electron／textlint継続）

    • textlint-rule-general-novel-style-ja を体裁チェックの中心にする
    • preset-ja-technical-writing は丸ごとではなく、ら抜き・助詞連続など文法系だけを抜き、文長・読点・！？禁止は切る／緩める
    • 固有名詞・ポリシーは prh に寄せ、辞書を作品ごとに育てる
    • 文体統一などは地の文前提の設定に寄せる（textlint 側で会話文の除外が難しいルールは情報レベルに落とす）

    novelaide（Tauri／Lindera自前実装）

    • 文字列層→辞書層→トークン層の順に段階実装する（下のフェーズ表）
    • 辞書層は novelaid-editor と同じ prh.yml を読める形式にし、辞書とルール設定ファイルを共通資産化する
    • ユーザー辞書CSV はルビ付与と共用し、登録UIを「登場人物辞書」として一本化する
    • スコープ制御（会話文の除外）は最初から土台に入れる。後付けはルール全書き換しになる

    実装フェーズ

    PHASE 1

    体裁と辞書（MVP）

    • 文字列層：字下げ、括弧対応、三点リーダー、！？後スペース、記号重複
    • 辞書層：prh形式の表記統一（一人称・固有名詞）
    • スコープ判定の土台だけ先に入れる
    PHASE 2

    文法系（Lindera本番）

    • Lindera 統合とユーザー辞書CSV の読み込み
    • ら抜き、助詞の連続・重なり、誤用辞書マッチ
    • 地の文／会話文の適用範囲をルール設定に出す
    PHASE 3

    読みやすさと集計

    • 文体統一、文末表現の連続、一文の長さ（情報レベル）
    • 送り仮名ゆれ等の文書全体の集計レポート
    • 例外登録と、作品別ルールプロファイルの切り替え
    未確認・要検討：① 会話文の判定は「」の対応に依存するため、地の文中の短い引用や『』の入れ子での境界精度は実装時にサンプル原稿で検証が要る。② Lindera の details の並び順は辞書（IPADIC／UniDic）で異なるため、参照位置は辞書ごとに固定せず名前引きできる層を挟むのが安全。③ textlint-rule-general-novel-style-ja は最終更新が古く（npm 公開は約9年前の版が最新と表示される）、現行 textlint との組み合わせ検証は導入時に必要。

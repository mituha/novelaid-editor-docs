調査レポート

日本語校正・チェックライブラリ調査
textlint の現状と、Node.js / Rust の代替

小説執筆用デスクトップエディター（Electron 版＝Node.js、Tauri 版＝Rust）で使う日本語校正の選択肢を調べた。焦点は、現在使用中の textlint のメンテナンス状況と「バージョン不一致が起きやすい理由」、そして移行先があるかどうか。

調査日 2026年10月31日 前提 処理はローカル完結（本文を外部 API に送らない） 想定チェック 誤字脱字・ら抜き・二重否定・助詞の誤り／重なり・表記ゆれ・句読点・文体

結論

  1. textlint 本体は今も活発にメンテナンスされている。最新は v15.8.0（2026年8月1日）で、2026年に入ってからも v15.6〜v15.8 と複数リリースがある（直前の v15.5.0 は2025年12月7日）。Electron 版については「textlint を捨てる理由」は乏しく、バージョン固定の運用に切り替えて使い続けるのが第一推奨。
  2. バージョン不一致は偶然ではなく構造の問題。本体・プリセット・個別ルール・形態素解析層が別々の npm パッケージで、それぞれ異なる要求バージョンを持つ。プリセットは半年に一度のメジャー更新で依存を一括で引き上げるため、そのタイミングで壊れやすい。対策は「exact pin＋lockfile 固定＋年2回の計画的更新＋自前サンプル文での回帰テスト」。
  3. Node.js で textlint に代わる日本語校正ライブラリは、実質的に存在しない。日本語対応を名乗る他候補は、VS Code 拡張（ライブラリではない）、Java 製ツール（RedPen／LanguageTool、サイドカー運用）、Web サービス（Enno、外部送信）のいずれか。
  4. Rust にも日本語校正専用 crate は（本調査の範囲では）存在しない。Tauri 版は「Lindera＋校正ルールの自前移植」が本命。textlint-ja のルールは形態素トークンのパターンマッチが中心のため移植可能なものが多いが、工数は相応にかかる。2026年8月に登場した Rust 製日本語推敲 CLI「Suiko」は有望だが、対象は文章の自然さ・読みやすさで、ら抜き等はカバーしない。
  5. 小説用途では技術文書向けプリセットの丸ごと適用は不適切（感嘆符禁止、文長100字、弱い表現禁止など）。プリセット丸ごとではなく、個別ルールの選り抜き＋小説専用ルール（general-novel-style-ja）＋prh 辞書（登場人物名・表記ゆれ）が現実的な構成になる。
01

textlint 本体の現状 ― 問題は本体ではない

最新バージョンと 2025〜2026年のリリース状況（GitHub Releases を 2026-10-31 に直接確認）

  • v15.0.02025年6月22日 ― メジャーリリース Node.js 20 以上が必須に。旧 API（TextLintEngine、TextFixEngine、TextLintCore、シングルトン textlint）が削除され、createLinter() に一本化された。
  • v15.5.02025年12月7日
  • v15.6.02026年4月26日
  • v15.7.02026年5月14日 v15.7.1 が同年5月18日に続く。
  • v15.8.02026年8月1日 ― 最新 @textlint/kernel も同じく 15.8.0。ライセンスは MIT。

本体は「枯れたプロジェクト」ではない。2025年にメジャーバージョンを上げて旧 API を整理し、MCP 対応などの機能追加も続いている。組み込み API としては textlint パッケージが createLinter() / loadTextlintrc() を提供し、lintText(text, filePath) で文字列を直接 lint できる。.textlintrc を介さず低レベルに制御したい場合は @textlint/kernel を直接使う。

Electron 側の注意: textlint v15 は Node.js 20+ を要求する。使用中の Electron が内蔵する Node のバージョン（process.versions.node）が 20 未満だと v15 は動かない。Electron のバージョンと内蔵 Node の対応表そのものは本調査では未確認のため、実機で process.versions.node を確認してほしい。

ja-technical-writing がカバーする範囲

想定チェック（ら抜き、二重否定、助詞の重なり、句読点、文体、冗長表現、誤用）は、ほぼこのプリセット＋個別ルールでカバーできる。

文法・表現系

  • 二重否定を使わない、ら抜き言葉を使わない
  • 逆接の接続助詞「が」の連続、同じ接続詞の連続、同じ助詞の連続
  • 同一単語の連続（誤字候補）、よくある日本語の誤用、冗長な表現
  • 弱い日本語表現（〜かもしれない等）の禁止

表記・文体系

  • 文長 100 字以下、読点は 1 文 3 つまで、カンマ 3 つまで、漢字連続 6 字まで
  • 漢数字と算用数字の使い分け、ですます／である調の統一、文末句点「。」の統一
  • 感嘆符・疑問符の禁止、括弧の対応、不自然なアルファベット
  • UTF8-MAC 濁点、制御文字、ゼロ幅スペース、半角カナの禁止

不足するのは主に (a) 文脈依存の誤字脱字・誤変換（「紹介／照会」の区別などはどのルールベースツールでも困難）、(b) 表記ゆれ（prh 等の辞書型ルールの追加が必要）、(c) 小説固有の作法（下記の専用ルールが別途ある）。

小説向けに重要な個別ルール

  • textlint-rule-general-novel-style-ja ― 日本の小説の一般的作法: 段落先頭の字下げ（全角スペース）または開き括弧のみ許可、閉じ括弧の直前に句読点を置かない、！？の直後にスペース、三点リーダー（…）とダッシュ（―）は偶数個、句読点・中黒・長音符の連続禁止、アラビア数字の桁数制限など。バージョンと最新リリース日は未確認（Web 小説執筆者の利用例では ^1.3.0）。
  • @textlint-ja/textlint-rule-no-synonyms ― Sudachi 同義語辞書を使い「リポジトリ／レポジトリ」型の同義語表記ゆれを検出。
  • textlint-rule-ja-no-orthographic-variants ― 表記ゆれチェック。
  • textlint-rule-ja-simple-user-dictionary ― シンプルなユーザー辞書で校正するルール。prh と並んで作品固有語彙の受け皿になる。
  • 新規ルール textlint-rule-wording は Intl.Segmenter ベースの辞書型ルールだが、Node.js 22 以上の full-ICU 環境と textlint 15.3.0 以上が必須で、調査時点では「npm 公開前」と README に記載。将来の選択肢としてのみ把握しておけばよい。

03

バージョン不一致が起きやすい構造的な理由

「たまたま壊れた」のではなく、依存の組み方がそうなっている。

textlint 本体（kernel）@textlint/* はモノレポ内で同一バージョン・同時リリース ― ここは揃っている
↑ peerDependencies: textlint >= x.y.z（最低要求のみ宣言）
プリセットtextlint-ja 組織 ― 半年ごとにメジャー更新し、依存を一括で引き上げる
個別ルールtextlint-rule 組織・個人作者 ― それぞれ別ペースでリリース
↓ 形態素解析が必要なルールはここに依存
形態素解析層kuromojin 3.0.1 / kuromoji 0.1.2 ― ともに 2018年3月が最終リリース
  1. すべて独立した npm パッケージで、別組織・別作者が別ペースで出す。ルール側は peerDependencies に textlint: ">= x.y.z" の形で最低要求バージョンを宣言するのが公式作法。したがって「新しいルールを1つ足したら本体の引き上げが必要だった」が普通に起きる（例: preset-ai-writing は textlint 15.1.0+、textlint-rule-wording は 15.3.0+ と Node 22+）。
  2. プリセットの半年更新が「まとめ上げ」になる。ja-technical-writing の CHANGELOG では、メジャー更新のタイミングで Node 要件や sentence-splitter、kuromojin 等の依存メジャーが一括で上がる。小さな競合が半年分たまって一度に表面化する。
  3. 形態素解析層が 2018 年で止まっている。kuromoji 0.1.2 / kuromojin 3.0.1 は 2018年3月が最終リリース（Apache-2.0）。kuromojin は kuromoji のバージョンを pin して辞書の重複を避けていると明記しており、この層は「固定されたまま古い」。メンテナンス fork（@faanau/kuromoji）も出現している。
  4. 配置ずれでも壊れる。textlint とルールを別々の場所にインストールすると "Failed to load textlint's module" になることが FAQ にある。バージョンだけでなく、インストール構成そのものが壊れやすさに効く。
付き合い方（推奨運用）: 依存は ^ ではなく exact pin（完全固定）＋ lockfile をコミットし、更新はプリセットの半年サイクル（1月・7月）に合わせて年2回の計画的更新としてまとめて行う。その際、自前のサンプル文（引っかかってほしい文／引っかかってほしくない文のセット）で回帰テストを回し、検出結果の変化を確認してから本採用する。

Rust の選択肢 ― 校正専用 crate はなく、「土台＋自前ルール」が現実

crates.io で日本語校正そのものを行う crate は、本調査の範囲では確認できなかった。あるのは形態素解析器と、英語専用／外部依存のものだけ。

注目: Suiko（Rust 製・日本語推敲 CLI、2026年登場）

07

推奨構成

Electron 版は「残して運用を整える」、Tauri 版は「土台を選んでルールを移植する」。

textlint を継続し、バージョン固定の運用に切り替える

  • 本体は textlint v15 系を使い続ける。代替の npm ライブラリは実質存在せず、本体自体は活発に更新されている。移行コストに見合う行き先がない。
  • 依存は exact pin＋lockfile 固定。^ や ~ で浮かせず、更新は自分のタイミングでだけ行う。
  • 更新は年2回、プリセットの半年サイクル（1月・7月）に合わせて計画的に。その際、自前サンプル文セットで回帰テストを回し、検出の増減を確認してから採用する。
  • 構成はプリセット丸ごとではなく選り抜きで。ja-technical-writing から文法・表現系（ら抜き、二重否定、助詞の連続、冗長表現、誤用）を拾い、感嘆符・疑問符の禁止、文長100字、弱い表現の禁止など小説に合わないものは外す。
  • 小説作法は textlint-rule-general-novel-style-ja、表記統一は textlint-rule-prh（prh.yml に登場人物名・作品固有語を登録）。同義語ゆれには @textlint-ja/textlint-rule-no-synonyms。
  • 組み込みは createLinter() ＋ lintText() で文字列を直接 lint する形が v15 の作法。Electron 内蔵 Node が 20 以上か（process.versions.node）を先に確認する。

Lindera を土台に、textlint-ja のルールを自前移植する

  • 校正専用 crate はないので、「形態素解析＋ルール実装」が前提。土台は Lindera が第一候補: 純 Rust、辞書埋め込み可、ユーザー辞書が CSV（表層形, 品詞, 読み）で登場人物名にそのまま使える。ただしメジャーリリースが頻繁で API 変動が大きいため、バージョンは固定して使う。
  • 移植の見込み: textlint-ja のルールの多くは形態素トークン列のパターンマッチ（助詞の連続、二重否定、ら抜き、冗長表現の辞書照合など）なので、トークン形式を Lindera に合わせて書き直せば移植可能なものが多い。辞書型のもの（prh 相当）は YAML 辞書の読み込みから自前になる。
  • Electron 版と仕様をそろえる工夫: チェック項目の定義とサンプル文セット（回帰テスト）を両版で共有し、「同じ文には同じ指摘が返る」ことをテストで担保すると、二重管理の痛みが減る。
  • Suiko は補助として様子見。ら抜き等は対象外だが、「自然さ・読みやすさ」の推敲は textlint 系にない観点。CLI として呼べる形なら、書き上がった章の見直し用に後付けできる。ライブラリ利用可否は未確認。
  • sudachi.rs はユーザー辞書の反映に辞書ビルドが必要で運用が重く、Vibrato / Vaporetto はモデルの別途配布が必要 ― 組み込みの軽さでは Lindera が勝る。
